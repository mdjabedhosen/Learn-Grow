## Google OAuth `redirect_uri_mismatch` — root cause found: **port drift**

**Symptom:** every environment that was not production failed with Google's
`Access blocked: This app's request is invalid` / `Error 400: redirect_uri_mismatch`.

**Root cause (found by asking Google directly, not by guessing):** the OAuth
client's *Authorized redirect URIs* contains

| redirect_uri | Google verdict |
|---|---|
| `https://learnandgrow.io/api/auth/google/callback` | **ACCEPTED** |
| `http://localhost:5000/api/auth/google/callback` | **ACCEPTED** |
| `http://localhost:5005/api/auth/google/callback` | REJECTED |

The console was registered when the backend ran on **port 5000**. The backend
now runs on **5005** because macOS' Control Center (AirPlay Receiver) occupies
port 5000 permanently — verified on macOS 26.3.1, where the socket is bound
regardless of the `AirPlayReceiverEnabled` setting.

Google does **not** ignore the port for a `localhost` hostname: `localhost:5005`
is rejected while `localhost:5000` is accepted, and `127.0.0.1:5005` is rejected
too (the registered entry uses the *hostname* `localhost`, not a loopback IP, so
Google's loopback-port leniency does not apply).

**Fix:** register the URI the server actually sends —
`http://localhost:5005/api/auth/google/callback` — in the OAuth client.
Production is unaffected and already works.

**Guard rails added so this can never be a mystery again:**

- `npm run google:oauth:check` asks Google which URIs are accepted and
  **detects port drift automatically**, printing the exact URI to add.
- The backend now probes Google at startup and logs a loud warning naming the
  drift and the URI to add.
- `GET /api/auth/google` refuses to hand the browser to Google when the
  startup probe already proved the URI is unregistered. It redirects to the
  frontend login with `?error=google_not_configured&redirect_uri=...`, and the
  login page shows the exact URI to register — instead of Google's generic
  "Access blocked" page.
- `resolveGoogleCallbackUrl` is now **port-aware**: it prefers the allow-list
  entry matching the port the server is actually listening on, so the same
  build works on 5000 or 5005.
- `GOOGLE_CALLBACK_URLS` now lists the 5000, 5005 and production URIs, so one
  deployment serves every environment.

### Admin role change from the dashboard — FIXED

**Symptom:** In `Admin → Users`, editing a user and picking a different role reported
*"User updated successfully!"*, the list refreshed — but the stored role never changed.
An admin could not change anyone's role.

**Root cause:** the admin dashboard sends the role in the `PUT /api/users/admin/:id`
body (`learn-grow/app/admin/users/page.tsx` → `handleEditUser` → `role: editForm.role`).
`updateUserAdmin` in `grow-backend/src/modules/user/service/user.service.ts` built its
`$set` from a hand-written whitelist —

```ts
if (updates.name) toSet.name = updates.name;
if (updates.email) toSet.email = updates.email;
if (updates.phone) toSet.phone = updates.phone;
if (updates.password) toSet.password = await bcrypt.hash(updates.password, 10);
if (typeof updates.isBlocked === 'boolean') toSet.isBlocked = updates.isBlocked;
// <-- `role` was never read, so it was silently dropped
```

The function's own type signature accepted `role: string`, so nothing complained. The
`$set` simply never contained it, the write succeeded, and the response was a truthful
*"User updated"* about a no-op. The dedicated `PATCH /admin/:id/role` endpoint
(`updateUserRoleAdmin`) did work — but no page called it.

**Fix:**
- New `grow-backend/src/modules/user/service/adminUserUpdate.ts` — `buildAdminUserUpdate()`
  builds the `$set` and **applies `role`**, validating it against the allowed list and
  rejecting anything else. Setting `role: "instructor"` also sets `isApproved: true`,
  because an admin assigning the instructor role *is* the approval step.
- `updateUserAdmin` now uses that helper and passes `runValidators: true`.
- `updateUserRoleAdmin` gained the same validation (it previously had **no** validation and
  `findByIdAndUpdate` does not run validators by default, so an arbitrary string could be
  written to `role`) and now accepts `"manager"` — it was missing from its type union.
- `createUserAdmin` gained the same role validation.
- Single source of truth for roles: `USER_ROLES` / `UserRole` / `isValidUserRole` are
  exported from `grow-backend/src/modules/user/model/user.model.ts` and now drive the
  Mongoose enum, the Zod schemas and the services, so a role can never be accepted by one
  layer and rejected (or dropped) by another.

**Verification** (all against the live database and the running dev servers):

| Check | Command | Result |
|---|---|---|
| Unit tests for the update builder | `npm test` | 12/12 pass (55/55 total) |
| Service + DB round trip | `npm run verify:role-change` | role persisted, demotion persisted, invalid role rejected & DB untouched, dedicated endpoint works |
| HTTP round trip (the exact dashboard request) | `npm run verify:role-change:http` | `PUT /admin/:id` → 200 → role visible over HTTP; `PATCH /admin/:id/role` → 200; invalid role → 400 |
| Full UI round trip in real Chrome | `npm run verify:role-change:ui` | login → Admin/Users → Edit User → Instructor → Save Changes → list badge reads **INSTRUCTOR** and the DB row reads `instructor` |

### C-2 · Unauthenticated account takeover + role escalation

**File:** `grow-backend/src/modules/user/routes/user.routes.ts:16`
```ts
router.post("/select-role/:userId", controller.selectRoleForGoogleUser); // NO auth
```
**Service:** `grow-backend/src/modules/user/service/user.service.ts:1630-1648`
```ts
const user = await User.findById(userId);
user.role = role;            // no isNewGoogleUser check, no auth check
user.isNewGoogleUser = false;
await user.save();
const { accessToken, refreshToken } = generateTokens(userId, role);
user.refreshToken = refreshToken;
await user.save();
return { success: true, data: { accessToken, refreshToken, user: {...} } };
```

**Impact:** No auth middleware, and the service never checks `isNewGoogleUser`. Any anonymous caller can:
1. Read admin `_id`s from public endpoints (`GET /api/users/instructors/approved`, `GET /api/team`)
2. `POST /api/users/select-role/<adminId>` body `{"role":"instructor"}` → **rewrites the admin's role** and returns a valid accessToken for that account

Result: takeover of any account with a known ID, self-escalation student→instructor, and persistent DoS on admin accounts (their role is destroyed).

**Fix:** Add `requireAuth`; use `req.userId` — never a URL param — as the target; require `user.isNewGoogleUser === true`; allow only `student|guardian`.

### C-14 · Quiz auto-submit at 0:00 scores 0 and discards every selected answer

**File:** `learn-grow/app/quiz/[id]/QuizClientPage.tsx:69-83` (timer effect) + `:95-136` (`handleSubmitQuiz`)
```tsx
useEffect(() => {
    if (quizSubmitted || !quiz) return;
    const timer = setInterval(() => {
        setTimeLeft((prev) => {
            if (prev <= 1) {
                handleSubmitQuiz();   // ← stale closure over `answers`
                return 0;
            }
            return prev - 1;
        });
    }, 1000);
    return () => clearInterval(timer);
}, [quizSubmitted, quiz]);          // ← `answers` is NOT a dependency
```
```tsx

    quiz.questions.forEach((question, index) => {
        const userAnswer = answers[index];   // ← frozen at the render where the effect last ran
```

**Impact:** The interval callback captures `handleSubmitQuiz` from the render in which the effect last ran — the render right after `quiz` loads, when `answers === {}`. **Fix:** Keep the latest handler in a ref and call it outside the updater:
```tsx

submitRef.current = handleSubmitQuiz;
// inside the interval:
if (prev <= 1) { setTimeout(() => submitRef.current(), 0); return 0; }
```
